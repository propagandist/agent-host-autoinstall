\section{はじめに}
%======================================================================

\subsection{この手順書の目的}
手元に置く物理 PC を、AI コーディングエージェント(Claude Code、Codex ほか)を
Orca で並列に動かす「常時稼働のエージェントホスト」にするための手順をまとめる。
USB メモリ 1 本からほぼ無人でインストールでき、再起動やセッションの異常終了のあとも人手を介さずに、
RDP で接続できる状態に戻ることを目指す。

仕様は \code{docs/SPEC.md}、調べたこと・確かめたことと未確認の事項は \code{docs/notes.md} にある。
この手順書と食い違ったときは、リポジトリの文書とスクリプトを正とする。

\subsection{なぜ Orca で動かす専用の PC を用意するのか}\label{sec:why}
コーディングエージェントは、1 つの作業に数十分から数時間かかり、確認なしで動かすことも多い。
人の役割は、作業を任せ、承認や質問に答え、できたものを見比べて選ぶことに移る。
そうなると「エージェントをどこで動かすか」が問題になる。置き場所ごとに比べると次のとおり(2026-10-25 時点の各社の文書と、このリポジトリで確かめたことによる)。

\noindent{\small\begin{tabularx}{\linewidth}{@{}p{0.2\linewidth}p{0.22\linewidth}L@{}}
\toprule\headrow
置き場所 & 向いていること & この用途で足りないこと \\
\midrule
手元の PC & 短い作業。すぐ自分で手を入れたいとき &
  動いているあいだ閉じる・持ち出す・再起動することができない。
  私的なファイルや個人のログイン情報と同じ環境で、確認なしのエージェントを動かすことになる。並べるほどメモリと CPU を取り合う \\
クラウドのエージェント(Claude Code の cloud sessions、Codex cloud) & 手元を閉じても続く。各社が隔離した環境で動く &
  各社のエージェントごとに別々で、1 つの画面で並べて見比べられない。
  リポジトリは GitHub が前提(Claude Code の文書では、GitHub 以外のリポジトリは送れても push で戻せない)。
  各社の環境からは LAN の中の Gitea や検証用のサーバーに届かない(組織で自前の実行環境を用意する仕組みはある)。
  使わない時間が続くと環境が片付けられる \\
クラウドの VM で同じものを動かす & 置き場所を選ばない &
  動かし続けるほど費用がかかる(金額は比べていない)。LAN の資源には VPN が要る。
  この手順の USB からの導入は物理の PC を前提にしている \\
\textbf{専用の PC(この構成)} & LAN の中で Orca を動かし続け、どの PC やスマホからも同じ画面に入る &
  PC の用意と置き場所、壊れたときの交換は利用者が持つ。ディスクは暗号化しない(\ref{sec:caution} 節) \\
\bottomrule
\end{tabularx}}

\medskip
\noindent\textbf{専用の PC で得られること}
\begin{itemize}
  \item \textbf{閉じても止まらない。}RDP を切っても作業は続き、つなぎなおせば同じ画面に戻る(受け入れテスト 6)。
        再起動・電源断・セッションの異常終了のあとも、人手なしで RDP まで戻る(受け入れテスト 3・4・8。VM で自動の試験がある)
  \item \textbf{任せる範囲を分けられる。}確認なしのエージェントは、読んだ Web ページや入れたパッケージの中の指示に従ってしまうことがある。
        専用の PC の、sudo のない専用のユーザーで動かせば、私的なファイルや個人のログイン情報には届かない。
        影響はその PC の作業と、その PC でログインしたサービスの範囲にとどまる(ログインする範囲は絞っておく)
  \item \textbf{LAN の中の資源を使える。}LAN の Gitea、検証用のサーバーやデータベースに、そのまま届く。
        プロキシや独自の CA 証明書がある LAN にも合わせられる(env.yaml の \code{proxy}、\code{ca_certs})
  \item \textbf{取り合わない。}エージェントを並べても、手元の PC の動きは重くならない。メモリは 32GB 以上を勧める
  \item \textbf{同じものを作りなおせる。}USB メモリ 1 本から、同じ構成を何度でも作れる。2 台目からの管理は \code{docs/fleet.md}
\end{itemize}

\noindent\textbf{Orca を中心に置く理由}
\begin{itemize}
  \item \textbf{Orca 自身が「作業する PC」と「操作する PC」を分ける使い方を想定している。}Orca の文書の Remote Orca Server では、
        作業する側がプロジェクト・worktree・端末・エージェントのセッションを持ち、ノート PC やブラウザ、スマホは画面になる。
        ノート PC が眠ってもエージェントは動き続ける。この構成は、その作業する側を OS ごと人手なしで保つもの
        (利用者ごとのセッション、キーリング、RDP、落ちたときの立てなおし、UPS は Orca の範囲の外なので、ここで用意する)
  \item \textbf{特定の会社のエージェントに縛られない。}Claude Code と Codex に加え、OpenCode・Copilot CLI・Antigravity CLI も同じ画面に並べられる。
        同じ作業を別々のエージェントに任せて結果を比べることも、得意なものに振り分けることもできる
  \item \textbf{並べてもぶつからない。}エージェントごとに git の worktree を分けるので、同時に進めても互いのファイルを壊さない
  \item \textbf{人が詰まりにならない。}承認待ちとエラーを Slack と IP Messenger に知らせ、スマホからも様子を見て答えられる
        (Orca Mobile、Claude Code の Remote Control)
\end{itemize}

\noindent\textbf{なぜデスクトップと RDP か(画面のない \code{orca serve} ではなく)}
\begin{itemize}
  \item エージェントのログインにブラウザが要る(Claude Code は Chrome でログインする。GitHub やクラウドの SSO も)。
        Orca の文書でも、ログインは作業する側で行い、ノート PC のログインは引き継がれない
  \item RDP なら、Windows に最初からあるリモート デスクトップ接続でつながり、手元に何も入れなくてよい。
        手元の Orca から作業する側につなぐ方法(Remote Orca Servers)はベータで、手元にも Orca が要る(使う場合は \ref{sec:remote-orca} 節)
  \item エージェントが Chrome で画面を確かめる作業も、人が VS Code やファイルを触って手を入れる作業も、同じデスクトップでできる
  \item そのかわり、パスワードなしで立てるセッション・空パスワードのキーリング・画面のロックなし、という妥協がいる(\ref{sec:caution} 節)
\end{itemize}

\noindent\textbf{向かない場合。}作業が短く、リポジトリが GitHub にあり、LAN の資源が要らないなら、クラウドのエージェントで足りることが多い。
物理の PC を置けない・管理できないときも向かない。両方を使い分けてもよい。

道具としての Orca の比較(ほかの ADE や TUI)は、\ref{sec:apps} 節の終わりにある。

\subsection{対象読者}
このリポジトリを使って、AI エージェントのためのホストを用意・運用する人。
Linux の基本的な操作(端末、SSH、apt)ができることを前提とする。

\subsection{この手順書の読み方}
コマンドの枠の右上に、どこで打つかを書いている。
\begin{local}
just status <ホスト>     # 手元の PC(リポジトリの直下)で打つ
\end{local}
\begin{host}
sudo systemctl reboot    # just ssh などでホストに入り、sysadmin で打つ
\end{host}
\begin{term}
gh auth status           # RDP で入った自分(利用者)のデスクトップの端末で打つ
\end{term}
\begin{hint}
\code{<ホスト>} はホスト名か IP アドレスに置き換える。囲みは、\textcolor{cautioncol}{\textbf{注意}}(誤ると戻せないこと)、
\textcolor{hintcol}{\textbf{ヒント}}(知っておくと楽なこと)、\textcolor{checkcol}{\textbf{確認}}(確かめること)の 3 種類。
\end{hint}

\subsection{できあがる環境}
\begin{itemize}
  \item OS: Ubuntu Desktop 26.04 LTS(GNOME 50。GNOME のセッションは Wayland のみ)
  \item 遠隔操作: GNOME のリモート デスクトップ(RDP)。利用者ごとに画面のない(ヘッドレスの)GNOME のセッションを立て、
        それぞれ自分のポート(env.yaml の \code{users[].port}。例 3389、3390)で待ち受ける。モニターは要らない
  \item 管理: SSH(\code{sysadmin} ユーザー、鍵認証のみ)
  \item エージェント: Orca(ADE)、Claude Code、Codex、選択で OpenCode・GitHub Copilot CLI・Antigravity CLI
  \item 開発環境: Node.js、Python(uv)、mise、rootless Docker、GitHub CLI、Gitea CLI、Google Chrome、
        エディター(選択。拡張機能も入る)、クラウドの CLI(選択。AWS・Google Cloud・Azure)
  \item 通知: Slack と IP Messenger(承認待ち・エラー・完了)
\end{itemize}

\subsection{ユーザー}
\noindent{\small\begin{tabularx}{\linewidth}{@{}lllL@{}}
\toprule\headrow
ユーザー & 用途 & sudo & ログイン \\
\midrule
\code{sysadmin} & OS の管理・更新 & あり & SSH(鍵認証のみ)。コンソール \\
利用者(env.yaml の \code{users}) & Orca とエージェントの実行。1 人に 1 ユーザー & なし & 起動のときに systemd がヘッドレスのセッションを立てる(パスワードはロック)。RDP は自分のポートと自分の認証情報で入る。SSH は SFTP 専用(鍵を登録した人だけ) \\
\bottomrule
\end{tabularx}}

\code{admin} は Ubuntu の予約名でインストーラーに拒否されるため、管理ユーザーは \code{sysadmin} にしている。
利用者は 1 人に 1 ユーザーで、Claude Code・Codex などのログイン(サブスクリプション)は本人のホームに置く。
1 台を複数の人で使えるが、ログインは人ごとに分け、共有しない。ホームは本人だけが読める(700)。ただし \code{sysadmin}(root)は全員のホームを読める。
メモリの目安は、1 人あたり 0.5〜1GB(GNOME のセッションと RDP。エージェントとビルドは別。VM で測った)。
0.2 までの \code{agent} ユーザーは、env.yaml の \code{users} に \code{name: agent} と書けば、そのまま利用者の 1 人として使える。

セキュリティ上の問題、費用その他の損害について、作成者は責任を負わない(Apache License 2.0 の第 7 条・第 8 条)。
\end{caution}

\paragraph{守る前提}
\begin{itemize}
  \item \textbf{LAN の中だけで使う。}SSH(22)と RDP(利用者ごとのポート)は \code{lan_cidrs} の範囲だけに許可する。インターネットに開けず、LAN の外からは VPN などを通す
  \item \textbf{PC は関係者だけが触れる場所に置く。}利用者のセッションはパスワードなしで立ち、画面のロックも止めている。RDP のパスワードが、利用者どうし(と各自のサブスクリプション)を隔てる実質の唯一の境界になるので、本人が最初の RDP で仮の値から変える(\ref{sec:rdp} 節)
  \item \textbf{利用者のホームに置く秘密は、各サービスのログインの情報だけにする。}ログインキーリングは空パスワードで、ディスクも暗号化しない。PC やディスクを持ち出されれば中身を読まれる。\code{sysadmin}(root)は全員のホームを読める
\end{itemize}

\paragraph{知っておくこと}
\begin{itemize}
  \item \textbf{エージェントは確認なしで動く。}Orca の確認なしでコマンドを実行するモードは最初からオン。sudo は渡さないが、作業のディレクトリのファイルの削除、ログイン済みのサービスへの push や送信、API の利用料の発生は起こりうる
  \item \textbf{コードとデータは外部のサービスに送られる。}送ってよい情報かは、組織の規程や契約で確かめる
  \item \textbf{版を固定したソフトには、セキュリティ更新が自動では入らない。}apt で hold したもの、/opt に置いたもの、npm で入れたツール、VS Code の拡張機能は、利用者が版を上げて反映する(\ref{sec:versions} 節)。OS のセキュリティ更新と Google Chrome は自動で入る
  \item \textbf{ほかのソフトとサービスの規約・ライセンスは、利用者が同意するもの。}インストールのときに各社の配布元から取得する(再配布はしない)。契約が要るものもある
  \item \textbf{止められない通信がある。}たとえば Orca の更新の確認は止める手段がない
  \item \textbf{秘密情報が入るファイルがある。}ISO と USB、env.yaml、移行の書き出し、手元の \code{build/} の一時ファイル、ホストの \code{/opt/agent-host/env.sh} と \code{/opt/agent-host/users/}(と \code{/opt/agent-host.prev/} の同じもの)、\code{/etc/agent-host/notify.env}、\code{/etc/nut/}。IP Messenger の通知は暗号化されない
\end{itemize}

環境ごとの値(秘密情報を含む)は \code{autoinstall/env.yaml} に書く。

just check-env common.yaml hosts/agent-host-01.yaml

\code{just fetch-iso} は、Ubuntu の公式のサイト\footnote{\url{https://releases.ubuntu.com/26.04/}}から
Desktop の ISO と SHA256 の一覧を取得する。

\subsection{just iso がすること}
\code{scripts/build-usb.sh} を呼ぶ。
\begin{enumerate}
  \item env.yaml を検査し、値を埋めた \code{autoinstall.yaml} と、スクリプト用の \code{env.sh}・公開鍵・CA 証明書を作る
  \item ISO の直下に \code{/autoinstall.yaml} と、スクリプト一式 \code{/agent-host/} を足す
  \item grub.cfg の起動行に \code{autoinstall} を足す(確認画面を出さないため)
  \item 元の ISO の起動の構成(BIOS と UEFI)を保ったまま書き出す
\end{enumerate}

\subsection{USB に書き込む}
\code{build/agent-host.iso} を、Rufus なら「DD イメージ」のモードで書き込む。Linux なら \code{dd} を使う。
env.yaml は安全な場所に保管しておく(入れなおしや移行で使う)。

\begin{caution}
できた ISO と USB には、パスワードのハッシュ、RDP のパスワード、Slack の Webhook の URL、UPS のパスワード(netclient のとき)が入る。
使い終わったら消す。この USB から起動すると、\textbf{確認なしでディスク全体を消してインストールが始まる}。
対象以外の PC に挿したまま起動しない。
\end{caution}

\section{BIOS の設定}
%======================================================================
\begin{checklist}
  \item 「Restore on AC Power Loss」(名称は機種による)を \textbf{Power On} にする
  \item UEFI で起動する。USB から起動できるようにする
  \item NVIDIA の GPU で Secure Boot が有効なら、そのままにしておく(インストールの中で入る NVIDIA のドライバーが署名済みのモジュールで動くかは未確認。動かなければ \code{just verify} の「GPU」で失敗が出る)

\subsection{UPS(env.yaml の ups を書いた場合)}\label{sec:ups}
\code{85-ups.sh} が NUT(Network UPS Tools)で UPS を見て、バッテリーが少なくなるか NUT サーバーが指示したら、正しく終了する。

\end{itemize}

\subsection{結果を確かめる}
\begin{local}
just status <ホスト>    # 置いた版と成功した版・構成・待ち受けのポート・利用者のセッション・ディスク・メモリ・失敗した unit
just logs <ホスト>      # 構成・利用者ごとの first-login とセッションの記録
just verify <ホスト>    # 仕様どおりかを確かめる(全体と利用者ごと。読むだけ。sudo のパスワードを聞かれる)
just verify-rdp <ホスト> # 利用者ごとに、仮のパスワードで RDP の認証が通るか(画面は開かない)
\end{local}

\begin{confirm}
\code{just status} で「構成: 済み」と、利用者の RDP のポートの待ち受け、利用者ごとの「セッション: あり」が出て、
失敗した unit がないこと。\code{just verify} の最後が「○ 項目のうち ○ 項目が通った」で、失敗した項目がないこと。
\end{confirm}

構成が失敗したときは、原因を直してから \code{just update <ホスト>} で再実行する。
スクリプトは冪等で、何度流しても同じ状態になる。

\begin{hint}
構成の記録に \code{RDP server certificate is invalid} や \code{Init TPM credentials failed} が出ることがあるが、
最終的な状態は正常で、RDP も待ち受ける(原因は未調査)。

\code{just verify-rdp} は、env.yaml の仮のパスワードで確かめる。本人がパスワードを変えたあとは、その人の分は
「未検証」と出る(失敗ではない)。今のパスワードで確かめるなら \code{just verify-rdp <ホスト> --ask <利用者>} で聞かれる値を入れる。
つながらない、TLS のエラーなど、認証の前で止まったものは失敗になる。
\end{hint}

\subsection{RDP でつなぐ}\label{sec:rdp}
\begin{local}
just rdp <ホスト> <ポート>   # build/<ホスト>-<ポート>.rdp を作る(Windows のリモート デスクトップ接続用)
\end{local}
接続先は \code{<ホスト>:<その人の port>}(env.yaml の \code{users[].port})。ユーザーとパスワードは、その人の \code{rdp.username} と
\code{rdp.initial_password}(仮の値)。RDP のクライアントは何でもよい
(Windows のリモート デスクトップ接続(mstsc)、Linux の Remmina や FreeRDP、macOS の Windows App など)。
\code{just rdp} が作る接続ファイルは mstsc 向けで、Windows キーを常にホストへ送り、クリップボードを共有し、
色を 24 ビットにし(同じ 26.04 で mstsc の 32 ビットは遅いという報告がある。ただしグラフィックス パイプラインではホストが 32 ビットで送るので、ホストの負荷は変わらない)、回線の自動検出を有効にする(遅延の大きい回線で、ホストが送る量を絞りすぎない)。ほかのクライアントでも、同じ設定にするとよい。
初回は証明書の警告が出る(自己署名のため)。mstsc では「このコンピューターへの接続について今後確認しない」を選ぶと、次から出ない。

\begin{caution}
\textbf{最初の RDP で、自分の RDP のパスワードを変える。}env.yaml の仮の値は、ISO や構成リポジトリを扱う人が知っている。
RDP のパスワードは、利用者どうし(と各自のサブスクリプション)を隔てる実質の唯一の境界になる。
\begin{term}
grdctl --headless rdp set-credentials <ユーザー名> <新しいパスワード>
systemctl --user restart gnome-remote-desktop-headless.service
\end{term}
ユーザー名は env.yaml の \code{rdp.username} と同じにする。2 行目で RDP のデーモンを再起動するまでは古いパスワードのままになる
(デーモンは起動したときの認証情報を使い続ける)。再起動すると今の接続が切れるので、新しいパスワードで入りなおす
(セッションと端末の中の処理は続く)。TPM のない機械では「Init TPM credentials failed …」と出るが、ファイルに保存したという意味で、失敗ではない。just update と移行のあとも、変えた値が残る
(just update は、認証情報がまだないときだけ仮の値を入れる)。端末の履歴にパスワードが残るので、気になるなら打ったあとに
\code{history -d} で消す。

忘れたときは、管理者が \code{sysadmin} で \code{sudo rm <利用者のホーム>/.local/share/gnome-remote-desktop/credentials.ini}
としてから \code{just update} を行うと、仮の値に戻る。
\end{caution}

\begin{caution}
Claude Code や Codex などのサブスクリプションは個人の契約なので、ログインを複数の人で共有しない(規約に反するおそれがある)。
1 台を複数の人で使うときは、env.yaml の \code{users} に人数分を書き、それぞれが自分のポートと自分のパスワードで入り、
自分のアカウントでログインする。ほかの利用者のホームは読めない。開発サーバーのポート(\code{dev_ports})は全員で取り合う。
\end{caution}

\subsection{手元の Orca からつなぐ(Remote Orca Server、ベータ)}\label{sec:remote-orca}
手元の PC の Orca を画面にして、このホストの Orca を操作する(Orca の機能。Orca ではベータ)。
プロジェクト・worktree・端末・エージェントのログインはホストに置いたままで、手元の PC が眠っても、つながりが切れても、作業は続く。
手元の PC にも Orca が要る。手順は Orca の公式の文書(Remote Orca Servers、2026-10-28 に読んだもの)から書いた。
LAN の IP を選び、\code{dev_ports} に 6768 を足した状態で、手元の Orca からつながることを確かめた。
\begin{caution}
リンクを持つ人はエージェントを丸ごと操作できる。リンクはパスワードと同じに扱う。
許可は手元の PC ごとに出るので、使わなくなった PC はホストの Orca の Shared Server Access で取り消す。
新しいリンクを作ると、まだ使っていないリンクは無効になる。ポートをインターネットに直接開けない(LAN の外からは VPN か Tailscale など)。
\end{caution}
LAN からつなぐなら、Orca が待ち受けるポートを env.yaml の \code{dev_ports} に足して \code{just update}(\code{lan_cidrs} からだけ開く)。
ポートは Orca Mobile と同じ 6768(リンクの中の接続先が \code{ws://<LAN の IP>:6768} だった)。2 人目以降の利用者でポートがずれるかどうかは、Orca Mobile と同じに扱う。
\begin{enumerate}
  \item ホストで(RDP で入る): Orca の Settings → Remote Orca Servers → Advertise this app as a server で \textbf{New Link}。
        Connection address に LAN の IP か Tailscale のアドレスを選び(127.0.0.1 は選ばない)、\textbf{Generate Access Link}。
        Pair another Orca client の下に出るリンクをコピーする
  \item 手元の PC で: Orca の Settings → Remote Orca Servers → \textbf{Add Server}。名前を付けてリンクを貼り、\textbf{Add Server}。
        Disconnected と出たら \textbf{Connect}
  \item プロジェクトを全部ホストで動かすなら、手元の Orca の Advanced → Active Server でホストを選ぶ
\end{enumerate}
\begin{itemize}
  \item ログイン: エージェントはホストのログインを使う。手元のログインは引き継がれない(この章のログインで足りる)
  \item 版: ホストの Orca は 1.4.237 に固定して hold している。手元の Orca と版が違うと、非互換のプロトコルと出て切れることがある。
        そのときは手元の Orca をホストの版に合わせるか、ホストの版を上げる(\ref{sec:versions} 節。未確認)
  \item このホストで使わないもの: \code{orca serve}(デスクトップの Orca がすでに公開しているので、重ねて起動しない。Orca の文書の注意)。
        Orca の SSH worktrees(利用者の SSH は SFTP 専用で、ポート転送も止めているので使えない)
\end{itemize}

\subsection{ファイルのやり取り}
env.yaml の \code{users[].ssh_authorized_keys} に公開鍵を書いた人は、SFTP でその利用者に入れる(シェルには入れない)。
作業の置き場所は \code{/home/<利用者>/work}。Windows では WinSCP\footnote{\url{https://winscp.net/}} を使う。
\begin{checklist}
  \item 「新しいサイト」で、転送プロトコル \code{SFTP}、ホスト名 \code{<ホスト>}、ポート 22、ユーザー名 \code{<利用者>}

\end{host}

FileZilla は公式サイトの標準のインストーラーにほかのソフトの勧誘が付くので、付かない版を選ぶ。
小さなファイルは RDP のクリップボードでも渡せる(未確認)。

\subsection{定期的な再起動}
unattended-upgrades はセキュリティ更新を自動で入れるが、作業中のエージェントを止めないよう自動では再起動しない。
カーネルなどの更新は再起動するまで反映されないので、\textbf{月 1 回、エージェントが作業していない時間に再起動する}。
\begin{local}
just ssh <ホスト>
\end{local}
\begin{host}
[ -f /var/run/reboot-required ] && cat /var/run/reboot-required.pkgs
sudo systemctl reboot
\end{host}
再起動後は何もしなくても RDP で接続できる状態に戻る。

\subsection{設定やバージョンを変える}\label{sec:versions}
env.yaml を直したとき、スクリプトや固定するバージョン(スクリプトの先頭の版と SHA256)を直したときは、
OS を入れなおさずに反映できる。
\begin{caution}
版を固定したソフト(apt で hold した Claude Code、Docker、GitHub CLI、Orca、VS Code、Google Cloud CLI、Azure CLI、
/opt に置いた Node.js・Gitea CLI・uv・mise・Zed・AWS CLI・Antigravity CLI、npm で入れたツール、VS Code の拡張機能)には、セキュリティ更新が自動では入らない。各ソフトのセキュリティ情報を見て、
スクリプトの先頭の版を上げ、ここの手順で反映する(付録 A に固定している版の一覧がある)。
\end{caution}
\begin{local}
just update <ホスト>    # env.yaml から設定を作りなおし、スクリプトを入れ替えて、構成を再実行する
\end{local}
\noindent{\small\begin{tabularx}{\linewidth}{@{}p{0.36\linewidth}p{0.16\linewidth}L@{}}
\toprule\headrow
env.yaml の項目 & just update で & 注記 \\
\midrule
\code{hostname}・\code{network}・\code{keyboard_layout} & \textbf{反映しない} & インストールのときだけ効く。変えるなら入れなおす \\
\code{sysadmin} & 反映する & 鍵とパスワードを env.yaml の内容に置き換える \\
\code{users} & 反映する & 足した人は作ってセッションを立てる。外した人はユーザーとホームを残して止める(\ref{sec:users} 節)。\code{rdp.initial_password} は、その人に RDP の認証情報がまだないときだけ入る(本人が変えた値は上書きしない) \\
\code{desktop_color} & 反映する(セッション) & セッションが動いていればその場で、そうでなければ次にセッションが立つときに(Dock も) \\
\code{editors}・\code{agents}・\code{clouds}・拡張機能 & 足すだけ & 外しても消さない \\
\code{lan_cidrs}・\code{dev_ports} & 足すだけ & ufw の許可は外しても消えない \\
ほか(\code{proxy}・\code{ca_certs}・\code{notify}・\code{ups} など) & 反映する & 利用者の環境変数は、次にセッションが立つときに効く \\
\bottomrule
\end{tabularx}}
\begin{itemize}
  \item env.yaml のホスト名と、つないだホストの名前が違うと止まる(別のホストの設定を流さないため)
  \item 元の一式はホストの \code{/opt/agent-host.prev} に残る
  \item sysadmin の SSH の鍵とパスワードは、env.yaml の \code{sysadmin} に置き換わる(手で足した鍵や \code{passwd} で替えたパスワードは戻る)。鍵を替えるときは、今つないでいる鍵を外さない順で行う。反映のあと入りなおせるかを確かめ、入れなければ止まって知らせる
  \item NVIDIA の GPU があるのにドライバーが入っていないと、構成の記録に注意が出る(\code{sudo ubuntu-drivers install} のあとに再起動)
  \item 途中で失敗すると \code{just status} に「前回の実行が最後まで終わっていない」と出る。\code{just logs} の「最後の just update」で止まったスクリプトを見て、直してから just update する
  \item 壁紙の色と Dock は、env.yaml か入っているエディターが変わったときだけ入れなおす(自分で変えた Dock は、それまで残る)
  \item RDP の認証情報は本人が変えるもので、just update では入れ替わらない(戻すときは \ref{sec:rdp} 節)
  \item 反映したら \code{just verify <ホスト>} で、固定の版と設定が仕様どおりかを確かめる
  \item 利用者のセッションが動いていると、その人の環境変数の変更は次にセッションが立つときに反映される(再起動か、その人のセッションを落とす)
  \item Chrome は Google のリポジトリに最新版しかないため固定せず、unattended-upgrades が自動で上げる
\end{itemize}
\begin{caution}
ufw の許可は足すだけなので、\code{lan_cidrs} や \code{dev_ports} から外したものは手で消す
(\code{just ssh} → \code{sudo ufw status numbered} → \code{sudo ufw delete <番号>})。
\end{caution}

\subsection{利用者を足す・外す}\label{sec:users}
env.yaml の \code{users} を直して \code{just update} する。\code{port} は人に固定し、ほかの人と重ねない。
\begin{itemize}
  \item \textbf{足す}: ユーザーを作り、RDP を設定し、セッションを立てる。本人は仮のパスワードで入り、最初に変える(\ref{sec:rdp} 節)
  \item \textbf{外す}: ユーザーとホーム(ログインと作業)は残す。ログインを止める(期限切れにし、SSH の \code{AllowUsers} から外す。
        鍵の SSH・SFTP も拒まれる)。セッション、linger、ユーザーのサービス(rootless Docker を含む)、ufw のその人の RDP のポートも止める。
        env.yaml に戻すと、同じユーザーとホームで使える
  \item ホームを消すときは、外したあとに \code{sysadmin} で \code{sudo userdel -r <利用者>} を行う(戻せない)
  \item 通知は \code{[ホスト名/利用者名]} で届くので、誰のエージェントかが分かる
\end{itemize}

\paragraph{0.2 から上げるとき}
0.2 までの env.yaml の \code{rdp}・\code{git_user_name}・\code{git_user_email}・\code{agent_ssh_authorized_keys} は使えなくなった
(書き換え先を出して検査で止まる)。\code{users} の 1 人目を \code{name: agent}、\code{port: 3389} にすれば、
今のホーム、ログイン、RDP の証明書をそのまま使える。\code{rdp.password} は \code{rdp.initial_password} にする
(0.2 で入れた認証情報はキーリングにあり、ヘッドレスの RDP には引き継がれないので、この値が入る)。
\code{dev_ports} が利用者の port と重なっていると止まる(例 \code{"3000:3999"} は 3389 を含むので、\code{"3000:3099"} などにする)。
\begin{caution}
上げたときの \code{just update} の途中で GDM を再起動するので、0.2 の自動ログインのセッション(端末、Orca、動いているエージェント)は終わる。
作業していない時間に行う。
\end{caution}

\subsection{環境を入れ替える(OS の入れなおし、機種の交換)}
ホストの身元(SSH のホスト鍵、RDP の証明書)、ログインと設定(エージェント、GitHub・Gitea の CLI、クラウドの CLI、Orca、エディター)、\code{~/work} と Orca の worktree を移す。
ツールの本体、mise の言語、Docker のイメージ、Chrome のプロファイルは移さない(作りなおせる)。
\code{~/work} の中の \code{node_modules}・\code{__pycache__}・\code{.venv} と Orca のキャッシュも除く(取り込みの最後に、除いたものが出る。\code{npm install} や \code{uv sync} で作りなおす)。
ほかの名前(\code{dist}、\code{target} など)は、ビルドの出力でも除かない。
利用者全員のホームを書き出し、取り込むのは新しいホストの env.yaml の \code{users} にいる名前の分だけ(同じ名前で合わせる)。
ホームの分は、書き出しも取り込みもその利用者の権限で行うので、取り込んだものはその利用者の持ち物になる。
利用者に読めないもの(rootless Docker のコンテナが作ったデータなど)は書き出さず、書き出しと取り込みの最後に一覧が出る(移すなら、元のホストで読めるようにしてから書き出しなおす)。
RDP の認証情報(本人が変えたもの)はホームごと移る(TPM のある機械では TPM に入るので移らない見込み。未確認。移らなければ just update で仮の値が入る)。

\centering

\begin{enumerate}
  \item Orca とエージェントの作業を止める
  \item 書き出す(ホストには保存されない。sudo のパスワードを 1 回聞かれる)
\begin{local}
just backup <ホスト>    # build/backups/<ホスト>-<日時>.tar.zst に書き出す
\end{local}
  \item Docker のボリュームに残したいデータがあれば、手で書き出す
  \item 同じ env.yaml で \code{just iso} を作り、新しいホストを入れる
  \item 取り込むまでは一時の \code{known_hosts} でつなぐ。新しいホストの画面(RDP の端末でもよい)で指紋を見て、最初に出る指紋と照らす
\begin{host}
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
\end{host}
\begin{local}
export AGENT_HOST_SSH_OPTS="-o UserKnownHostsFile=$PWD/build/known_hosts.migrate"  # ほかの指定があれば後ろに足す
just status <ホスト>    # 指紋が同じなら yes
\end{local}
  \item 構成が終わったら取り込み、再起動する
\begin{local}
just restore <ホスト> build/backups/<ホスト>-<日時>.tar.zst
unset AGENT_HOST_SSH_OPTS; rm -f build/known_hosts.migrate
just ssh <ホスト>       # sudo systemctl reboot(元の known_hosts でつながる)
\end{local}
  \item \code{just verify <ホスト>} と、受け入れテストの 4・5 を行う
\end{enumerate}

\begin{caution}
書き出したファイルにはログインの情報が入る。暗号化された場所に置き、取り込んだら消す。
\end{caution}
\begin{hint}
入れなおすと SSH のホスト鍵が新しくなり、取り込むと書き出したときの鍵に戻る。そのため取り込むまでは、手元の \code{known_hosts} と合わず
「REMOTE HOST IDENTIFICATION HAS CHANGED」で止まる。\code{known_hosts} の古い鍵は消さない(取り込んだあとにもう一度食い違う)。
確かめずにつなぐ設定(\code{StrictHostKeyChecking=no})は、書き出しと sudo のパスワードを確かめていない相手に送ることになるので使わない。
\end{hint}

\end{caution}

\section{just を使わない場合}
%======================================================================
just のレシピがしていることを手で行うときのコマンド。リポジトリの直下で実行する。

\subsection{ISO を作る}
Linux(\code{xorriso} と \code{python3-yaml} が要る):
\begin{local}
curl -fLO https://releases.ubuntu.com/26.04/ubuntu-26.04.1-desktop-amd64.iso
curl -fsSL https://releases.ubuntu.com/26.04/SHA256SUMS | sha256sum -c --ignore-missing
scripts/build-usb.sh ubuntu-26.04.1-desktop-amd64.iso \
    build/agent-host.iso autoinstall/env.yaml
\end{local}
Windows では、Git Bash から Docker の Ubuntu の中で同じことをする。
\begin{local}
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/repo" -w /repo \
  ubuntu:26.04 bash -c 'apt-get update -qq &&
  apt-get install -y -qq xorriso python3-yaml &&
  bash scripts/build-usb.sh build/ubuntu-26.04.1-desktop-amd64.iso \
    build/agent-host.iso autoinstall/env.yaml'
\end{local}

just を使わずに ISO を作ったり更新したりすると、置いた版の記録(\code{BUILD-INFO})が置かれず、\code{just status} は「記録なし」、
\code{just verify} は「置いた版の記録がある」で失敗する(\code{build-usb.sh} と \code{stage.sh} に \code{--build-info <ファイル>} で渡せる)。

\subsection{状態と記録を見る}
\begin{local}
ssh sysadmin@<ホスト>
\end{local}
\begin{host}
test -f /var/lib/agent-host/provisioned && echo 構成済み
ss -tln                                             # 利用者の RDP のポート
systemctl status 'gnome-headless-session@*'         # 利用者ごとのセッション
sudo journalctl -u agent-host-provision.service    # 初回の構成
sudo tail -40 /var/log/agent-host-update.log        # 最後の just update
sudo cat /home/<利用者>/.local/state/agent-host/first-login.log
sudo /opt/agent-host/verify.sh     # 仕様どおりかを確かめる(just verify と同じ)
\end{host}

\subsection{設定やスクリプトを変えたとき}
\code{scripts/stage.sh autoinstall/env.yaml <作業ディレクトリ>} で \code{<作業ディレクトリ>/agent-host/} を作り、
ホストの \code{/opt/agent-host} と入れ替えてから(\code{env.sh}・\code{users/} の中・\code{sysadmin_authorized_keys} は 600、\code{users/} は 700、所有者は root)、
\code{sudo /opt/agent-host/provision.sh} を実行する。

\subsection{移行の書き出しと取り込み}
\code{sysadmin} の sudo はパスワードが要り、標準入力は書き出しの受け渡しに使うので、
パスワードは標準入力の先頭の 1 行で渡す。
\begin{local}
read -rsp "sysadmin のパスワード: " PW; echo
printf '%s\n' "$PW" | ssh sysadmin@<ホスト> \
    'sudo -S -p "" agent-host-backup' > agent-host-<ホスト名>-<日付>.tar.zst
{ printf '%s\n' "$PW"; cat agent-host-<ホスト名>-<日付>.tar.zst; } |
    ssh sysadmin@<ホスト> 'sudo -S -p "" agent-host-restore'
unset PW
\end{local}

\subsection{RDP の接続ファイル}
\code{docs/agent-host.rdp.example} をコピーし、\code{full address} を \code{<ホスト>:<その人の port>} に直す(改行は CRLF のまま)。

\subsection{手順書の PDF}
リリースした版の PDF は、GitHub の Releases に付いている。手元で作るときは \code{just guide}(Docker が要る)。
just を使わないときは、スクリプトを直接実行する。
\begin{local}
scripts/local/build-guide.sh     # build/setup-guide/setup-guide.pdf
\end{local}

  \item rootless Docker のコンテナの中でメモリが詰まったとき、systemd-oomd がほかのコンテナも一緒に止めるか
\end{itemize}
